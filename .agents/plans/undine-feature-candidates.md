# Undine feature candidates

This is one deduplicated list of features that Undine could add.
We compared 47 GraphQL frameworks against Undine. Each framework has a findings file in `.agents/plans/findings/`.
Six batches turned the findings into candidate lists (`.agents/plans/feature-gap-work/candidates-1.md` to `candidates-6.md`).
Each batch compared its findings against the Undine inventory (`.agents/plans/feature-gap-work/undine-inventory.md`).
This file merges the six lists. Rows that describe the same feature are one row here.
When batches disagreed on "Undine today", I checked `undine/` and `docs/` with grep and wrote what is true.
When batches disagreed on Fit, the Notes column says which fit I picked and why.
Rows or claims marked "I think" are not verified in the Undine code.

Count (by grep on the Fit column): high 7, medium 129, low 296. Total 432 candidate rows. 14 rows dropped (see the end of the file). 3 possible bugs.

## Possible bugs

These are places where Undine behaves wrongly today. They are not only missing features.

| Bug | What happens | Where | Seen in (candidate rows) | Notes |
|---|---|---|---|---|
| 64-bit integer fields map to 32-bit `Int` | `BigIntegerField`, `PositiveBigIntegerField` and `BigAutoField` are subclasses of `IntegerField`. The converter maps them all to `GraphQLInt`. `GraphQLInt.serialize(2**31)` raises "Int cannot represent non 32-bit signed integer value". So a value above 2147483647 fails on output, and the same value is rejected as input. Django's default primary key type (`DEFAULT_AUTO_FIELD`) is often `BigAutoField`, so large primary keys also fail. | [ undine/converters/impl/convert_to_graphql_type.py:565 ] [ undine/converters/impl/convert_model_field_to_python_type.py:59 ] | strawberry-sqlalchemy: `BigInt`. graphene-django: `BigInt`. graphene: `graphene.BigInt`. gqlgen: `graphql.Int64`. async-graphql: `StringNumber<T>`. hasura: `STRINGIFY_NUMERIC_TYPES`. pg_graphql: `BigInt` as string | I ran `GraphQLInt.serialize(2**31)` and it raised. I checked that `BigAutoField` and `PositiveBigIntegerField` are `IntegerField` subclasses. Fix: a `BigInt` scalar (string or number) for these fields. |
| DataLoader reused loads are shared across requests | A `DataLoader` is a module-level object (see the docs example). `reusable_loads` is an attribute on that object. So concurrent requests in one ASGI process share reused loads. The `request_finished` receiver calls `clear_all()`, so one request that finishes also clears the loads of other requests that are still running. WebSocket operations do not send `request_finished` (no other hit for the signal in `undine/`). So in a WebSocket-only process, reused loads are never cleared. The docs say reused loads "are not shared between requests". | [ undine/dataloaders.py:69 ] [ undine/dataloaders.py:217 ] [ docs/dataloaders.md:141 ] | strawberry: fresh loaders per request. envelop: `useContextValuePerExecuteSubscriptionEvent`. pothos: `clearAllDataLoaders(context)` | I verified the code paths. I think the effects are stale data in long subscriptions, memory growth on WebSocket workers, and results reused between users when `load_fn` closes over request data. I did not write a test. Fix idea: store reused loads per operation (for example in a `contextvars.ContextVar` or on `info.context`). |
| Request errors return HTTP 200 with `"data": null` | `graphql_result_response` always uses status 200. The views do not pass another status. `get_error_execution_result` builds `ExecutionResult(data=None)`, so request errors (bad body, parse error) include `"data": null`. This also happens with `Accept: application/graphql-response+json`. | [ undine/http/responses.py:52 ] [ undine/http/views.py:46 ] [ undine/utils/graphql/utils.py:197 ] | yoga: `extensions.http.status`. hasura: `PRESERVE_401_ERRORS`. hot-chocolate: `OnDetermineStatusCode` | I think the GraphQL over HTTP spec says that with `application/graphql-response+json` a request error should get a 4xx status, and that a response without a `data` entry must not use 2xx. I think the GraphQL spec also says `data` should not be present when an error happens before execution. I did not re-read the spec text for this list. The test `test_graphql_view__async__parse_error` asserts 200 with `application/json`, which is correct for that media type. |
